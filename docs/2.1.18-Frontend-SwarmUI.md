### [SwarmUI](https://github.com/mcmonkeyprojects/SwarmUI)

> Handle: `swarmui`<br/>
> URL: [http://localhost:35050](http://localhost:35050)

SwarmUI is a modular AI image/video generation web UI (grid-based batch generation, a
ComfyUI-powered node workflow tab, model browsing, etc.) built on top of a ComfyUI backend that
it installs and manages itself.

![SwarmUI screenshot](./harbor-swarmui.png)

> [!NOTE]
> Unlike [`comfyui`](./2.1.2-Frontend&colon-ComfyUI.md), which runs a pinned, unmaintained
> `ghcr.io/ai-dock/comfyui` image (ComfyUI v0.2.2, torch built for the cu121 wheel index — no
> `sm_120` kernels), SwarmUI clones ComfyUI fresh on first launch and installs torch from the
> **cu130** wheel index, which does carry Blackwell (`sm_120`, RTX 50-series) kernels. If
> `comfyui` fails to use your RTX 50-series GPU, this is the Harbor service to reach for instead.

> [!IMPORTANT]
> No pre-built SwarmUI image is published upstream — Harbor builds it from source. Run
> `harbor build swarmui` before first `harbor up swarmui`, and again on **every** host you run
> it on, since the image bakes in that host's `HARBOR_USER_ID` as a Dockerfile build arg.

#### Starting

```bash
harbor build swarmui   # builds from source, no pre-built image exists upstream
harbor up swarmui --open
```

First launch is slow twice over: the dotnet build happens during `harbor build`, then SwarmUI's
own first-run install wizard (in the browser) clones ComfyUI into the `dlbackend` volume and
downloads several GB of torch and its CUDA dependencies. Watch progress with:

```bash
docker logs -f harbor.swarmui
```

In the install wizard, select the **NVIDIA** backend option so it installs from the cu130 wheel
index described above (see [`comfy-install-linux.sh`](https://github.com/mcmonkeyprojects/SwarmUI/blob/master/launchtools/comfy-install-linux.sh) upstream). AMD/Intel GPUs are not
supported by Harbor's overlay — SwarmUI's own Docker docs disclaim a known-working setup for
either.

#### Configuration

##### Environment Variables

SwarmUI itself reads no environment variables for configuration — all settings are either CLI
args or stored in `Data/Settings.fds` once you configure them in the UI. `services/swarmui/override.env` therefore has no effect on the service; the variables below only exist to
build and place the container itself, so `harbor env swarmui` is not useful here.

Following options can be set via [`harbor config`](./3.-Harbor-CLI-Reference.md#harbor-config):

```bash
# Web UI port on the host
HARBOR_SWARMUI_HOST_PORT      35050

# Git source SwarmUI is built from (branch/tag pin via #ref)
HARBOR_SWARMUI_GIT_REF        https://github.com/mcmonkeyprojects/SwarmUI.git#master

# Persistent data root — holds Data/, dlbackend/ (the installed ComfyUI +
# venv), dlnodes/, and extensions/
HARBOR_SWARMUI_WORKSPACE      ./services/swarmui/workspace

# Host path mounted as SwarmUI's Models folder
HARBOR_SWARMUI_MODELS         ./services/swarmui/models

# Host path mounted as SwarmUI's Output folder
HARBOR_SWARMUI_OUTPUT         ./services/swarmui/output

# Extra CLI args appended to SwarmUI's launch script, e.g. --lock_settings
HARBOR_SWARMUI_ARGS           ""
```

Use the [`harbor swarmui`](./3.-Harbor-CLI-Reference.md#harbor-swarmui) CLI to manage the two
most commonly-touched settings without invoking `harbor config` directly:

```bash
harbor swarmui args ["--flag ..."]  # Get/set extra launch args
harbor swarmui models [path]         # Get/set the host Models folder path
harbor swarmui output                # Open the Output folder in the File Manager
harbor swarmui workspace             # Open the workspace folder (Data/dlbackend/extensions) in the File Manager
```

##### Sharing models with `comfyui`

`HARBOR_SWARMUI_MODELS` defaults to its own directory (`./services/swarmui/models`) rather than
pointing at the existing `comfyui` service, so the two don't fight over the same files by
default. To avoid re-downloading checkpoints you already have via `comfyui`, repoint it:

```bash
harbor swarmui models ./services/comfyui/workspace/storage/stable_diffusion/models
harbor down swarmui && harbor up swarmui
```

SwarmUI expects Comfy-style model subfolders (`Stable-Diffusion`, `Lora`, `VAE`, `ControlNet`,
etc.) under whatever path you mount here — the layout ai-dock's `comfyui` provisioning script
already produces is compatible enough for basic use, but SwarmUI's own model-metadata scan may
not recognize every folder name without adjustment. See [SwarmUI's Model Support
docs](https://github.com/mcmonkeyprojects/SwarmUI/blob/master/docs/Model%20Support.md) for the
expected structure.

##### Volumes

- `${HARBOR_SWARMUI_WORKSPACE}/data` → `/SwarmUI/Data` — settings, sessions, presets, user DB.
- `${HARBOR_SWARMUI_WORKSPACE}/dlbackend` → `/SwarmUI/dlbackend` — the ComfyUI clone the install
  wizard creates, plus its Python venv. This is where the multi-GB torch download lands.
- `${HARBOR_SWARMUI_WORKSPACE}/dlnodes` → `/SwarmUI/src/BuiltinExtensions/ComfyUIBackend/DLNodes`
  — ComfyUI custom nodes SwarmUI installs on your behalf.
- `${HARBOR_SWARMUI_WORKSPACE}/extensions` → `/SwarmUI/src/Extensions` — SwarmUI's own
  extensions.
- `${HARBOR_SWARMUI_MODELS}` → `/SwarmUI/Models` — checkpoints, LoRAs, VAEs, etc. (see above).
- `${HARBOR_SWARMUI_OUTPUT}` → `/SwarmUI/Output` — generated images/videos.

The container runs as `HARBOR_USER_ID:HARBOR_GROUP_ID` with `cap_drop: [ALL]`, matching
upstream's own `docker-compose.yml`. A `swarmui-init` sidecar (alpine) pre-creates and chowns all
six paths above to that UID/GID before the main container starts — SwarmUI's own entrypoint
refuses to start with a "Detected folder ownership issue" message if it finds root-owned
directories while running as a non-root user, which is what happens if Docker is left to create
these bind-mount targets itself. **On macOS this is handled differently** — see
[Running on macOS](#running-on-macos) below.

##### Git metadata

SwarmUI's own startup code shells out to `git` to read its current commit (shown in logs and
used for its update check) and refuses to run properly ("Improper Download Warning") without a
real `.git` directory. Two things make that work given Harbor builds from a remote git context:

- `BUILDKIT_CONTEXT_KEEP_GIT_DIR: "1"` build arg — BuildKit strips `.git` from remote-git build
  contexts by default; this keeps it.
- `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0` environment variables — inject
  `safe.directory=*` into git's config. This is needed because the entrypoint script
  (`docker-standard-inner.sh`) overrides `$HOME` to a path under the `dlbackend` volume, which
  hides the `git config --global --add safe.directory '*'` set at build time (written to
  `/root/.gitconfig`, no longer on `$HOME`'s path at runtime) — without it, git refuses the repo
  with "detected dubious ownership".

##### Running on macOS

Docker Desktop for Mac's bind-mount layer does not apply `chown` to a non-root UID at all —
confirmed even the chowning container's own subsequent `stat` on the path reports `uid/gid 0`.
`swarmui-init` can never satisfy SwarmUI's ownership check on this platform as a result. Harbor
detects this (`has_macos()` in `harbor.sh`, active whenever `uname` is `Darwin`) and
auto-applies `services/compose.x.swarmui.macos.yml`, which runs `swarmui` as root
(`user: "0:0"`) with capabilities restored (`cap_add: [ALL]`, since root without
`CAP_DAC_OVERRIDE` still can't write files baked into the image under a different UID) — this
sidesteps the ownership check entirely rather than trying to satisfy it. This overlay is
macOS-only; the 5080-class Linux target uses the normal non-root path from the base compose
file, where `swarmui-init`'s chown works as intended.

#### Integrations

**Reverse proxy / external access**

- With `traefik` present: `compose.x.traefik.swarmui.yml` adds Traefik labels so the UI is
  reachable at `https://swarmui.${HARBOR_TRAEFIK_DOMAIN}` (websecure entrypoint, port derived
  from container port 7801).

**Hardware acceleration (GPU / accelerator)**

- NVIDIA passthrough is supplied by `compose.x.swarmui.nvidia.yml` (nvidia driver) or the
  CDI-generated `compose.x.swarmui.cdi.yml`.
- No AMD/ROCm overlay is provided — SwarmUI's own Docker docs explicitly disclaim AMD/Intel GPU
  support ("there's probably appropriate tooling for that. No idea what it is, good luck").

#### Troubleshooting

##### Rebuild after changing hosts or `HARBOR_USER_ID`

The image's user is created at build time (`useradd -u $UID`), baked from
`HARBOR_USER_ID` at the time you ran `harbor build swarmui`. If you move `services/swarmui/` to
a different machine, or your `HARBOR_USER_ID`/`HARBOR_GROUP_ID` change, rebuild:

```bash
harbor build swarmui
```

##### Check Logs

```bash
docker logs harbor.swarmui
```

`harbor logs swarmui` also works but tails by default — prefer `docker logs` for a one-shot look.
